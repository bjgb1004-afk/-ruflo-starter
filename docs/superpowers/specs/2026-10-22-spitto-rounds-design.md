# 스피또 회차 현황 — 설계

작성 2026-10-22. 승인됨.

## 무엇을 만드나

동행복권에서 스피또(즉석복권) 발행내역을 하루 1회 받아와, 지금 살 수 있는 회차와
**1등이 몇 매 남았는지**를 앱에 보여준다. 새 화면 1개 + 새 표 1개 + 수집 스크립트 1개.

## 왜 이걸 먼저 하나 (제보 기능보다)

유저가 원래 제안한 1순위는 "판매점에 스피또 있어요/없어요" 제보였다. 필요성은 실측으로
확인됐다 — 지금 판매중인 5개 회차의 입고율이 20·55·57·98·100%다. 즉 **절반 이상 회차는
가게 절반 이상에 아예 없다.** 공식 데이터로는 "그 가게에 있나"를 맞힐 수 없다.

그런데 지금 채울 수가 없다:

| | 값 |
|---|---|
| 판매점 | 10,000곳+ |
| 앱 유저 | 100명 미만 |
| 스레드 팔로워 | 840명 (평범한 글 300 조회, 터지는 글 10,000+) |
| 터지는 글 1건 → 앱 설치(통상 전환율 1~3% 어림) | 100~300명 |
| 그중 실제 제보까지 | 10~90곳 = **0.1~0.9%** |

제보함을 먼저 열면 유저가 어느 가게를 열어도 거의 빈칸이다. 2026-10-16에 통째로 지운
"사장님 인증"이 정확히 그 길이었다(테이블 3개 전부 0건, 한 번도 실사용 없음). 그 교훈은
"유저 데이터를 모으지 말라"가 아니라 **"유저 수에 비해 과하게 만들지 말라"**였다.

반대로 이 기능은 **유저 0명이어도 완성품**이다. 서버 데이터라 아무도 안 도와줘도 값이 나온다.
그리고 여기서 나오는 숫자가 스레드 글감이 된다:

> 스피또2000 70회 — 1등 8매가 **하나도 안 나갔다.** 아직 5곳 중 1곳에만 들어갔다.

그래서 순서는 이렇게 된다. **제보는 유저가 늘어난 뒤에 붙인다.**

```
회차 현황 → 스레드 글감 → 유저 증가 → 그때 제보가 채워진다
```

## 데이터 출처 (확정)

```
GET https://www.dhlottery.co.kr/st/selectPblcnDsctn.do
    ?gdsType=&gdsPrice=&gdsStatus=&pageNum=1&recordCountPerPage=50
```

- **로그인·쿠키 불필요.** 세션 없이 JSON을 준다.
- **빈 필터 3개(`gdsType`/`gdsPrice`/`gdsStatus`)를 "빈 값"으로 꼭 보내야 한다.**
  빼면 `{"resultCode":"fail.common.msg"}`만 온다. 이것 때문에 세 번 틀렸다.
- `recordCountPerPage=50`이면 전체 34개 회차가 1건의 요청으로 다 온다(`data.total=34`).
  페이징 불필요.
- 헤더는 `Referer`(발행내역 페이지)와 `X-Requested-With: XMLHttpRequest`를 같이 보냈을 때
  성공을 확인했다. 어느 쪽이 필수인지는 안 가려봤다 — 둘 다 보낸다.
- 응답: `{ resultCode, resultMessage, data: { total, list[], stRnkDate[] } }`

### `data.list` 한 건 (실측)

```json
{ "ntslStatus": "판매중", "stGmTypeCd": "SP2000", "stGmTypeNm": "스피또2000",
  "stEpsd": 70, "stSpmtRt": 20, "stNtslAmt": 2000, "stIvtRnk1Qty": 8,
  "stRnk1Rt": "8매/8매", "stRnk2Rt": "23매/24매", "stRnk3Rt": "195매/200매",
  "rnk1Atm": "10억원", "stNtslEndDt": "2026-12-31", "stGiveEndDt": "2027-12-31",
  "stMainImgStrgPathNm": "/img/board/content/202609/S2000_70_PC_Main_96dpi_...png",
  "ntslWnSn": 5808, "stExpsrYn": "Y", "dataChgDt": "26-10-16", "rowId": 1 }
```

### 필드 해석 — 추론한 것과 확인한 것을 구분한다

**`stSpmtRt` = 입고율(판매점에 들어간 비율). 확인됨.**
판매종료 68회가 입고율 100%인데 1등이 1매 남은 채 끝났다. 소진율이라면 100%는 전량 판매라
1등이 남을 수 없다 — 모순이므로 소진율이 아니다. 회차가 나이 들면서 100%로 수렴하는
움직임도 입고율과 맞는다(신상 70회 20% → 69회 98% → 종료분 대부분 100%).

**`stRnk*Rt`의 "N매/M매" = 잔여/전체. 추론.**
신상 70회가 입고율 20%인데 "8매/8매"다. 앞이 판매분이면 20%만 풀린 회차에서 1등 8매가 전부
팔렸다는 뜻이 되어 모순이다. 앞이 잔여면 "아직 아무것도 안 나갔다"로 자연스럽다. 종료된
68회 "1매/8매"도 "1매 안 나오고 끝"으로 읽힌다.
→ **구현 전에 발행내역 페이지의 열 제목을 직접 확인한다.** 화면에 "1등 8매 남음"이라고
쓰는 기능인데 뒤집혀 있으면 정반대를 말하게 된다. 열 제목이 애매하면 `stIvtRnk1Qty`(=8,
"8매/8매"의 뒷자리와 일치)가 총 발행 매수인지 다른 회차에서 교차 확인한다.

**보류**: `ntslWnSn`(5808), `stExpsrYn`("Y"), `rowId`(페이징 순번으로 보임) — 뜻을 모른다.
저장하지 않는다. 필요해지면 그때 본다.

**`data.stRnkDate`**: `{stGmTypeCd, ltEpsd, wnSqNo, dataChgDt, wnShpCnt}` 44건 — 회차·등수별
마지막 배출일과 **배출점 수**. 이번 범위에 안 쓴다(아래 "안 만드는 것").

## 저장

새 표 `spitto_rounds` 하나. **기존 표는 하나도 안 건드린다.** 로또 명당(지도·랭킹·판매점
상세)이 전부 `store_ranking_stats`에 걸려 있어, 거기에 복권 종류를 섞으면 잘 돌고 있는
기능이 깨진다 — 연금복권 조사에서 세운 원칙과 같다.

| 칼럼 | 출처 | 비고 |
|---|---|---|
| `game_type` text | `stGmTypeCd` | SP2000 / SP1000 / SP500 |
| `round_no` int | `stEpsd` | |
| `game_name` text | `stGmTypeNm` | "스피또2000" — 파생 가능하지만 받는 그대로 둔다 |
| `status` text | `ntslStatus` | 판매중 / 판매종료 |
| `stock_rate` int | `stSpmtRt` | 입고율 % |
| `price` int | `stNtslAmt` | 500 / 1000 / 2000 |
| `rank1_remaining`, `rank1_total` int | `stRnk1Rt` 파싱 | "8매/8매" → 8, 8 |
| `rank2_remaining`, `rank2_total` int | `stRnk2Rt` 파싱 | |
| `rank1_prize` text | `rnk1Atm` | "10억원" — 문자열 그대로. 숫자로 바꿀 이유 없음 |
| `sale_end_date` date | `stNtslEndDt` | 판매기한 |
| `claim_end_date` date | `stGiveEndDt` | 지급기한 |
| `image_path` text | `stMainImgStrgPathNm` | 동행복권 상대경로 |
| `source_changed_at` date | `dataChgDt` | "26-10-16" (YY-MM-DD) — 동행복권이 고친 날 |
| `synced_at` timestamptz | `now()` | 우리가 받아온 시각 |

기본키 `(game_type, round_no)`.

- **34개 회차를 전부 저장한다**(판매중만 걸러내지 않는다). 걸러내면 회차가 끝날 때 지우는
  로직이 따로 필요해진다. 그냥 전부 upsert하고 화면에서 `status='판매중'`으로 거르는 게
  코드가 더 짧다.
- RLS: 읽기는 `anon, authenticated` 전체 허용, 쓰기는 service role만
  (`generator_round_stats`와 같은 패턴). 개인 식별 정보가 없는 공개 데이터다.
- 용량: 34행 ≈ 10KB. Supabase 무료 500MB에 사실상 영향 없음.
- `database.types.ts`는 **손으로 블록을 추가한다.** 이 저장소에 타입 생성 스크립트가 없고
  `supabase gen types`도 로컬에 설정돼 있지 않다(사장님 인증 삭제 때 확인됨).

## 수집

`scripts/ingest/fetchSpittoRounds.ts`, `package.json`에 `ingest:spitto` 등록.
`scripts/ingest/lib/supabaseAdmin.ts`를 쓰는 기존 스크립트들과 같은 형태.

- **요청 1건/일.** 과거 IP 차단은 982회를 연속으로 때렸을 때 일어났고 임계치는 31 근처로
  봤다. 하루 1건은 근처도 아니다.
- `sync-data.yml`에 스텝 1개 추가. **이미 매일 새벽 3시(`cron: '0 18 * * *'` UTC)에 도는
  슬롯이 있다** — 새 cron을 만들지 않는다.
- 토요일 추첨 cron들에도 같이 붙지만 해롭지 않다(멱등 upsert). 원본이 실제로 바뀌는 건
  드물다 — 실측 `dataChgDt`가 6일 전이었다.
- GitHub Actions 비용: 저장소가 Public이라 무료 무제한. 추가 부담 0.
- 실패 처리: 이 스텝이 죽어도 **로또 수집은 계속되게 한다.** 워크플로 스텝에
  `continue-on-error: true`를 쓴다(스크립트 안에서 에러를 삼키는 쪽은 안 쓴다 — 실패가
  Actions 실행 이력에 남아야 나중에 눈에 띈다). 스피또는 부가 기능이라 본업을 막아선 안 된다.

## 화면

`app/(tabs)/more/spitto.tsx`. `more/index.tsx`의 `MENU_ITEMS`에 한 줄 추가
(`{ key: "spitto", emoji: "🎟️", label: "스피또 현황", href: "/more/spitto" }`).

- **판매중 회차만** 보여준다. 지금 5개.
- **정렬: 1등 남은 비율 높은 순.** 유저에게 가장 유리한 회차가 맨 위다. 평균 말고 최고를
  앞에 두는 원칙과 같다.
- 회차 카드 하나에: 상품명·회차 / **1등 "8매 중 8매 남음"** / 2등 잔여 / 입고율 / 판매기한.
- **입고율 60% 미만이면 안내 한 줄을 덧붙인다**: *"아직 N곳 중 1곳에만 들어왔어요 — 가게에
  전화로 확인하세요."* 기준선 60%는 실측 분포(20·55·57·98·100)에서 "거의 다 깔린
  회차(98·100)"와 "반도 안 깔린 회차(20·55·57)"가 갈리는 자리다. 상수로 빼서 조정 가능하게
  둔다. **"N곳 중 1곳"은 입고율에서 계산한다**(`round(100/stock_rate)`) — 20%면 5곳, 55%면
  2곳이다. 문구를 박아두면 회차마다 거짓말이 된다.
  제보 기능 없이 "그 가게에 있나"에 답하는 현재 최선이고, 판매점 상세에 전화번호와
  `tel:` 링크가 **이미 있다**.
- 데이터가 0건이면(첫 수집 전) **화면에 안내 한 줄을 띄운다.** 메뉴 항목을 조건부로 숨기는
  쪽은 안 쓴다 — 메뉴를 보이게 할지 판단하려고 목록 화면에서 미리 조회해야 해서 더 복잡하다.

## 배포

**순수 화면 + 서버 변경이라 OTA로 나간다. 네이티브 변경 없음 → 빌드 쿼터 0 소모**
(월 15회 중 하나도 안 쓴다).

```bash
npx eas update --branch main    --platform android --environment production --message "..."
npx eas update --branch preview --platform android --environment preview    --message "..."
```

`production` 채널이 보는 브랜치는 **`main`**이다(`--branch production`은 헛배포, 4번 반복한
실수). `--environment` 빼면 Supabase 접속값이 빠져 앱이 즉사한다. 배포 후
`npx eas channel:view production`으로 실제로 걸렸는지 확인한다.

## 검증 (여기서 끝내지 않는다)

1. 로컬에서 수집 1회 → 34행 들어오는지, 파싱이 맞는지
2. **1등 "N매/M매"의 앞뒤를 발행내역 페이지 열 제목으로 확인** (위 "추론" 항목)
3. 화면에서 5개 회차가 1등 잔여율 순으로 뜨는지
4. **수동 실행 성공은 "코드 버그 없음"까지만 증명한다.** 다음날 새벽 3시에 **저절로** 돈
   기록(Actions 실행 이력에 그 스텝이 찍혔는지)을 직접 확인하고 나서야 완료로 보고한다.
   같은 세션에서 못 기다리면 "코드는 됨, 자동실행은 미확인"이라고 말한다.

## 안 만드는 것

- **재고 제보** — 유저가 늘면. 조건: 스레드 글이 터져 설치가 실제로 늘었을 때, 또는
  "입고율 낮은 회차 어디 있냐"는 문의가 실제로 나올 때. 그때도 최소 버전으로
  (표 1개 + 버튼 1쌍 + 200m 반경, 제보 0건이면 그 칸을 아예 안 보여줘 죽은 기능처럼
  안 보이게). 현재 위치는 `src/hooks/useCurrentLocation.ts`가 이미 있다.
  **위치는 반경 안인지 확인만 하고 버린다 — 서버에 좌표를 저장하지 않는다.**

  ### 제보를 만들 때 반드시 먼저 읽을 것: 사용자 식별 수단
  (2026-10-22 이전 세션의 조사 결과. `docs/spito-handoff.md`에 있던 내용을 여기로 옮겼다.)

  현재 **일반 사용자는 로그인이 없다.** 이메일 로그인은 관리자 전용이다(설정 탭의 숨겨진
  제스처 → 비밀번호, 판별은 `ADMIN_EMAILS` + 서버 `is_admin()`). 그래서 제보를 받으려면
  식별 수단을 정해야 하고, 선택지가 셋이다:

  **A. Supabase 익명 로그인(`signInAnonymously`)** — RLS로 "본인 제보만 쓰기"를 걸 수 있어
  어뷰징 대응이 쉽다. 그런데 **익명 사용자도 `useAuth.user`가 null이 아니게 되면서 지금 잘
  도는 것 네 개가 조용히 깨진다**:
  - `src/features/favorites/useFavoritesCloudSync.ts` — 즐겨찾기 클라우드 동기화가 전원에게 시작됨
  - `app/(tabs)/more/favorites.tsx` — `isLoggedIn = !!user`라서 전원에게 "기기 간 동기화됨"이
    뜨는데, 익명 ID는 기기마다 달라 **거짓 문구**가 된다
  - `app/store/[id].tsx` — `toggleFavorite(..., userId)`가 익명 ID로 클라우드에 저장
  - 관리자 총 사용자 수 RPC(`auth.users` 개수)에 익명 계정이 섞여 의미가 바뀜

  A를 택하면 `isLoggedIn`을 `!!user && !user.is_anonymous`로 바꾸고 동기화도 같은 조건으로
  막아야 한다. `auth.users`에 익명 계정이 쌓이는 정리 정책도 따로 필요하다.
  (관리자 오인은 없다 — 판별이 이메일 기준이고 익명 사용자는 `email`이 없다.)

  **B. 기기 UUID만 로컬 저장** — 기존 인증에 영향 없지만 RLS로 본인 확인을 못 해 RPC나
  Edge Function을 따로 만들어야 한다.

  **C. 식별자를 아예 안 보낸다 (권장)** — `generated_tickets`와 같은 패턴. 보내는 것은
  `store_id` + 종류 + 있음/없음 + 시각뿐이고 기기 ID·토큰·계정이 없다. **위 A의 부작용 4개가
  처음부터 생기지 않고, B의 추가 구조물도 필요 없다.** 대가는 한 기기의 반복 제보를 서버에서
  못 막는 것인데, 200m 반경 확인이 이미 1차 방어이고 유저 100명 규모에서 조직적 어뷰징을
  가정하는 건 과하다. 막아야 할 상황이 실제로 생기면 그때 B나 A로 올린다.

  개인정보처리방침(루트·`docs/` 양쪽)과 구글플레이 데이터 안전 항목도 같이 손봐야 한다.
  C를 택하면 "익명으로 수집한 제보"로 한 줄이면 되고, A/B는 "익명 식별자"를 추가해야 한다.
- **스피또 명당·랭킹** — 안 만든다. 회차당 1등이 5~12매뿐이라 배출점 대부분이 "1회" 동률이
  되어 1위~300위가 전부 같은 값이 된다. 연금복권 조사에서 같은 이유로 접었고, 백테스트
  프리셋 화면이 "다섯 방법이 전부 같은 숫자"라 버려진 것과 같은 실패다.
- **스피또 배출점 지도 표시** — `stRnkDate`에 회차·등수별 배출점 수가 오지만 **좌표가
  없다.** 가게를 특정할 수 없으므로 지도에 못 올린다. 별도 조사가 필요한 다음 단계.
- **3등 잔여** — 응답에 공짜로 오지만(`stRnk3Rt`) 금액이 작아 안 쓴다. 칼럼 2개 추가면
  되니 원하면 그때 붙인다.
- **푸시 알림(신규 회차 떴을 때)** — 범위 밖. FCM이 아직 설정 안 돼 있어 네이티브 빌드가
  필요하다.
- **더 뒤의 아이디어들** — 당첨 인증(카메라, 일련번호는 받지 않음), 내 구매·당첨 기록(폰
  로컬), 제보자 등급·랭킹, 긁기 시뮬레이션. 전부 제보가 먼저 쌓여야 의미가 있다.
  착수 전에 구글플레이 사행성 정책과 19세 미만 안내를 확인할 것(복권을 경품으로 주는 건
  피한다). 원래 이전 세션 인수인계 문서에 있던 목록이고, 진행 여부는 백로그 메모리에서 관리한다.

### 화면 문구 원칙

이 앱은 **정보 제공**이다. 즉석복권은 온라인 판매가 안 되니 **구매를 부추기는 문구를 쓰지
않는다.** "1등이 다 나간 회차를 피할 수 있다"처럼 **손해를 막아주는 쪽**으로 쓴다. 지금
화면 문구는 이 기준으로 쓰여 있다.
