# 스피또(즉석복권) 추가 방안 - 전달 문서 (2026-10-22)

복권명당 앱에 스피또를 추가하는 작업의 결론과 진행 상황이다. 이 문서를 읽고 이어서 진행한다.
사용자는 답변을 **한국어로 간결하게** 받길 원하고, 확인 없이 단정하지 않기를 원한다.

## 1. 결정된 방향
- 앱의 성격은 **정보 제공**이다. 즉석복권은 온라인 판매가 안 되므로 구매 유도 문구는 쓰지 않는다.
- 사용자 폰을 활용한 크라우드소싱이 핵심이다. 판매점 재고는 동행복권에 없는 정보라서 제보로 채운다.
- **가장 먼저 만들 것은 "재고 제보" 하나뿐이다.** 등급/랭킹, 포인트, 당첨 인증, 긁기 시뮬레이션은 제보가 쌓이는지 본 뒤에 한다.
- 공식 데이터(어떤 회차를 살지)와 제보(어느 가게에 있는지)를 짝으로 보여준다.

## 2. 만들 기능 (우선순위 순)
1. **재고 제보 (최우선)**
   - 판매점 상세(`app/store/[id].tsx`)에 "스피또 있어요/없어요" 버튼, 종류별(500/1000/2000) 체크, "30분 전 확인" 표시.
   - 허위 제보 방지: 사용자가 판매점 반경 안일 때만 제보 가능. 위치는 서버에 저장하지 말고 **반경 안인지 확인만 하고 버린다.**
   - 중복 제보 방지: 같은 사용자가 같은 판매점에 짧은 시간 안에 반복 제보 못 하게 한다.
2. **스피또 회차 현황 (공식 데이터)** - 판매중 회차 목록, 판매점 입고율, 1등/2등 잔여수량, 판매기한. 아래 3번 참고.
3. 이후 단계: 당첨 인증(카메라, 일련번호는 가리거나 받지 않음), 내 구매/당첨 기록(폰 로컬 저장), 등급/랭킹, 푸시 알림, 긁기 시뮬레이션(마지막).

## 3. 공식 데이터 수집 - 차단 주의 (가장 중요)
- 동행복권은 연속 요청을 **IP째 끊는다.** 2026-09-28에 IP가 실제로 막혀 curl/ping도 죽었고 수십 분 뒤 복구됐다.
  자세한 기록: `scripts/ingest/rebuildWinStoresFromOfficial.ts` 상단 주석, `.github/workflows/rebuild-win-stores.yml` 상단 주석.
- 적용할 규칙: 요청 간격 1.5초 이상, 실패 시 1s/3s/7s 재시도, **연속 10번 실패하면 차단으로 보고 즉시 중단**(더 때리면 차단이 길어진다), 한 번에 적은 양만.
- 스피또는 회차 수가 적으므로 **하루 1~2회, 요청 몇 건**이면 충분하다. 연속 호출할 일이 없게 설계한다.
- 사용자 PC IP는 지금 막혀 있을 수 있다(2026-10-21 브라우저 접속이 ERR_CONNECTION_TIMED_OUT). 로컬에서 직접 호출하지 말고 **GitHub Actions 러너**에서 돌린다.
- 기존에 확인된 공식 JSON 주소(당첨판매점): `https://www.dhlottery.co.kr/wnprchsplcsrch/selectLtWnShp.do` (Referer 헤더 필요, 쿠키/세션 불필요). 요청 방식은 `scripts/ingest/lib/dhlotteryWinStores.ts` 참고.
- 구 경로(`store.do?method=topStore` 등)는 302로 막혀 있다.

- 표 항목: 판매상태, 상품명, 회차, 판매점 입고율, 1등 잔여수량, 2등 잔여수량, 판매가격, 1등 당첨금, 판매기한, 지급기한

## 4. Supabase 설계 (제안, 아직 미작성)
- `spito_issues`: 회차 현황 (상품종류, 회차, 입고율, 1등/2등 잔여, 판매가격, 1등 당첨금, 판매기한, 지급기한, 수집시각). 수집은 service_role로 쓰고 앱은 읽기만.
- `spito_stock_reports`: 재고 제보 (store_id -> `stores.id`, 사용자 id, 종류, 있음/없음, 제보시각). 앱에서 insert, RLS로 본인 제보만 쓰기. 판매점별 "최근 제보" 조회용 인덱스(store_id, 제보시각 desc).
- 등급은 제보 개수를 세서 계산하면 별도 관리가 필요 없다(후속 단계).
- 마이그레이션 파일명 규칙: `supabase/migrations/YYYYMMDDHHMMSS_설명.sql` (최근: 20261021000000_...).

## 5. 로그인 관련 (결정 필요)
- **현재 일반 사용자는 로그인이 없다.** 이메일 로그인은 관리자 전용이다(설정 탭의 숨겨진 제스처 -> 비밀번호 입력, `app/(tabs)/more/settings.tsx`).
  관리자 판별은 이메일 기준이다(`ADMIN_EMAILS` + 서버의 `is_admin()` / `admin_emails` 테이블). 익명 로그인은 아직 없다.
- 그래서 제보를 받으려면 사용자 식별 수단이 새로 필요하다. 선택지:
  - **A. Supabase 익명 로그인(`signInAnonymously`) - 권장.** 앱 첫 실행 때 자동으로 ID 발급. 이메일/비밀번호 입력이 없어 사용자에게는 로그인이 보이지 않는다.
    RLS에서 `auth.uid()`로 "본인 제보만 쓰기"를 걸 수 있어 어뷰징 대응이 쉽다. 단점: 앱 삭제/폰 교체 시 ID 소실.
    Supabase 대시보드에서 Anonymous Sign-ins 활성화가 필요하다.
  - B. 로컬에 저장한 기기 UUID만 사용(Supabase 인증 없음). 기존 인증 로직에 영향이 없지만, RLS로 본인 확인을 못 해서 어뷰징 방어가 약하고 RPC/Edge Function을 따로 만들어야 한다.
- **A를 택할 때 기존 코드에 생기는 부작용 (반드시 같이 처리):** 익명 사용자도 `useAuth.user`가 null이 아니게 된다.
  - `src/features/favorites/useFavoritesCloudSync.ts`: `userId`가 생기면 즐겨찾기 클라우드 동기화가 모든 사용자에게 시작된다.
  - `app/(tabs)/more/favorites.tsx`: `isLoggedIn = !!user`라서 모두에게 "기기 간 동기화됨"이 표시된다. 익명 ID는 기기마다 다르므로 거짓 문구가 된다.
  - `app/store/[id].tsx`: `toggleFavorite(..., userId)`가 익명 ID로 클라우드에 저장한다.
  - 관리자 총 사용자 수 RPC(`auth.users` 개수): 익명 사용자가 포함되어 의미가 바뀐다.
  - 관리자 판별은 이메일 기준이라 익명 사용자가 관리자로 오인되지는 않는다(`user.email`이 없음).
  - 해결 방향: `isLoggedIn`을 `!!user && !user.is_anonymous`로 바꾸고, 즐겨찾기 동기화도 같은 조건으로 막는다. 기존 동작(일반 사용자는 로컬 즐겨찾기)을 유지한다.
  - `auth.users`에 익명 계정이 계속 쌓이므로 정리 정책(예: 오래된 익명 계정 삭제)을 나중에 정한다.
- 개인정보처리방침(`docs/privacy-policy.html`)과 구글플레이 데이터 안전 항목에 "익명 식별자, 제보 기록"을 추가해야 한다.
- **사용자에게 A/B 중 선택을 확인한 뒤 진행한다.**

## 6. 정책/주의

## 7. 권장 진행 순서
1. probe Summary 확인 -> 발행내역 JSON 주소/응답 구조 확정
2. `spito_issues` 마이그레이션 + 수집 스크립트(`scripts/ingest/`) + 정식 워크플로(차단 방지 규칙 적용, DRY_RUN 지원)
3. 로그인 방식 결정(5번) -> `spito_stock_reports` 마이그레이션
4. 판매점 상세에 재고 제보 UI, 메인/탭에 회차 현황 화면
5. 타입체크(`npm run typecheck`)와 DRY_RUN 검증 후 커밋
